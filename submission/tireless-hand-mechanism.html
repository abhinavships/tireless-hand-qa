Three layers share one idea: never trust the screen alone. Compare it with an independent source (the backend, the messages the browser actually received, or the app's own other views).

2 · How it learns

The learner treats the cockpit as a black box. It never reads the source code. It watches two things at the same moments: what the screen shows and what data the browser just received. Then it asks, for every value on screen, "which piece of received data, formatted how, produces exactly this text?"

1

Explore

Open the app, list every element with a stable ID, and record which ones an operator can see and use at desktop, tablet and phone size. Find repeated per-entity elements (device-row-drone-3) to learn what the entities are.

2

Make the data move

Add a probe drone, select it and fly it: take off, climb, cruise, land. Moving values make the correlation unambiguous (a value that is always 0 could match anything).

3

Sample both sides together

24 times over about 16 seconds, read every on-screen text and, for the same instant, the last three websocket messages the browser received for that drone.

4

Score every candidate

For each on-screen value, try every field of every message: does field.toFixed(d), with the same number of decimals as the screen, reproduce the number? Count matches across samples, giving extra weight to matches on non-zero values.

5

Keep only strong bindings

A binding is accepted if it matches in at least 80 % of samples. Ties on zero-only values are kept as alternatives. Result: a binding such as telemetry-battery = battery.percent as "{0 dp} %".

6

Flag what can't be explained

Any measured value on screen (a number with a unit) that matches no received field is reported as unexplained. On a healthy build these are a few known items; on a broken build this is where the bug shows up.

3 · "Doesn't learning need a normal app? How can it then find bugs?"

Yes, and that is exactly the right question. Learning from the app assumes the build you learn from is healthy. If the build were already broken, a naive learner would learn the bug as "normal". The system handles this in three ways, and only one of them depends on learning.

Learned truth

Needs a trusted baseline

Bindings, the usable-element set per screen size, and which elements name the selected drone.

  • Baseline: the last released build. Here, the unmodified starter kit; the evaluators plant their bugs into exactly that build.
  • Catches: regressions, meaning anything a change breaks.
  • Like: the way a senior tester remembers how the app looked yesterday.
External truth

No baseline needed

The screen is compared with sources that don't come from the UI at all.

  • Device list = /api/devices
  • Telemetry = simulator state
  • Connection badge = our own independent connection
  • A drone name must never execute as code
  • Catches: bugs that were already in the product on day one (F2, F3 were found this way).
Consistency truth

No baseline needed

The app must agree with itself.

  • Device-list status = panel status
  • Selecting A → B → A shows only each drone's own data
  • After a fault clears, values recover without a reload
  • Data that has stopped arriving must not look live
  • Catches: contradictions, even if every single screen looks plausible (F1 was found this way).

4 · Proof: learning on a secretly broken build

We planted bug M05 (battery always shows 0 %) and then ran the learner on the broken build, as if it were the baseline. It did not accept the bug as normal:

=== learning on the clean build
  learned 10 bindings
   • telemetry-battery = battery.percent as "<0 dp> %"  [100%]

=== learning on a secretly broken build (M05)
  learned 9 bindings
  ⚠ unexplained value [data-testid="telemetry-battery"]: shows "0 %"
    but matches no field the UI received for this drone

A measured value that no received data can explain is suspicious by definition. So even a learner pointed at a broken build surfaces the bug, as an unexplained value for a human to confirm, instead of silently learning it. On the clean build the only unexplained measured value is wind, which comes from the dock's weather (a different entity) with a direction lookup; it is reviewed once and noted as expected.

7 · Limits, stated plainly

Baseline quality

Learned rules are only as good as the build they were learned from. Mitigated by external and consistency truth, and by reporting unexplained values instead of learning them.

Coverage of the generator

The generated scenario space covers the cockpit. Control-panel buttons, the video label's meaning and script injection are covered by the curated blind checks.

Values from other entities

The learner correlates with the selected drone's messages. Values derived from another entity (wind from the dock) stay unexplained until reviewed.
