Tireless Hand · Map QA explainer

How the Map QA Works

The FlytBase cockpit draws its map with Cesium, a 3D globe. The map is a single canvas, so there is no text in the page to read. This QA looks inside the map anyway and checks every drone against what the drone actually reported. It also works out new checks by itself: a local LLM proposes them, and the clean app decides which ones are real.

QA reads what the map draws, compares it with what the drone reported over the websocket, and any difference beyond the learned tolerance is a bug.

THE LOOPFrom a drone message to a verdict

1What the cockpit map is

Every drone and dock is an object in Cesium's scene: a 3D drone model, a dock icon, a text label such as "Drone 1 in_flight", a height label such as "30 m", a vertical height line and a flight track. All of it is painted into one <canvas>. Normal Playwright checks read DOM text, so on their own they cannot tell whether the drone is drawn in the right place.

2How QA sees inside the map

qa/map/anatomy.ts runs inside the page through Playwright (the Chrome DevTools Protocol). It starts at the map's <div>, walks React's internal fiber tree to Cesium's Viewer, and reads what the map is drawing. The product code is not changed.

  • Each object's latitude, longitude and height, converted from Cesium's 3D coordinates
  • The direction the drone model points, calculated from its rotation
  • Label text, icon image, model file and track points
  • The camera: where it looks and whether it is top-down
  • drillPick: what is actually drawn at a given pixel, which tells QA whether an icon is visible and clickable

3The truth it compares against

At the same time, QA records every websocket message the browser receives: the drone's real GPS position, height, yaw and flight status. That is what the map is supposed to show.

4The 15 checks

The inspector (map/inspector.ts) creates its own test drone, flies it, and checks the following. It deletes the drone afterwards.

CheckQuestion it answers
G1Does every drone and dock the backend knows have an object on the map?
G2Is the drone drawn where its GPS says it is (within 0.5 m)?
G3Does the height label match the real height, and is the 3D model at that height?
G4Does the model point the way the drone is facing?
G5Does the map label show the current flight status?
G6Does the dock-to-drone distance on the map match "Dist. from home" in the panel?
G7Does the flight track end at the drone and keep growing?
G8Is the drone visible at its pixel, and does clicking it select it?
G9Does selecting a drone fly the camera to that drone?
G10Is only the selected drone highlighted?
G11Is 2D really top-down and 3D oblique?
G12Does a deleted drone disappear, with its track and labels?
G13Do docks that stop sending data switch to the offline icon? The real app fails this; it is a product finding.
G14Does each new position reach the map quickly, or is the map showing an old message?
G15Icon census: exactly one known icon per device, none missing, none extra, none too small to see?

5The learner

You run npm run map:learn once on the clean app. It records what normal looks like: the icon files, the camera angles, and a 25-second test flight that measures how accurate and how fast the map is. Those measurements set the tolerances.

0 mposition error on the clean app
0°heading error
~80 msmessage → map, typical
~500 msbetween messages

The map is exact on this app, so most tolerances stay at their minimums. The timing matters: because a message normally reaches the map in about 80 ms, G14 can tell when the map is a whole message behind (bug MAP14), even though every position it draws is a real one.

6The agent discovers its own checks

The 15 checks above were written by hand. The agent also finds checks by itself with npm run map:discover. A local coding model proposes; the live app decides.

1 · ProposeLLM reads the map codeQwen2.5-Coder 7B on the RTX 5090 reads CesiumMap.tsx (about 400 lines) and one real websocket message per topic, and writes checks in a strict format. Asked 3 times at different temperatures, about 5 s each.
2 · VerifyClean app filters themEach check runs on every drone and dock while a test drone flies. A check that is false on the clean app is thrown away. That removes hallucinations.
3 · RepairEvidence goes backChecks that were false go back to the LLM with what the map really showed. Its corrections are verified again.
4 · KeepSaved and reusedSurvivors go to map/out/discovered.json, re-verified and merged on every run. npm run qa runs them as D1…D8 on the whole fleet.

Examples the filter caught. The LLM guessed the height label reads "Drone 1 0 m"; the map shows "0 m", so it was rejected. It proposed flight tracks for docks, which do not exist, so those were rejected too. In one repair it "fixed" a dock-height check by widening the tolerance to 1000 m. A check like that can never fail, so any check looser than 5 m or 5° is now rejected.

Proof. Planted bug MAP16 draws every dock icon 30 m east of its real location. None of the hand-written checks look at dock positions. Discovered check D5 flagged all 8 docks: "Dock 1 … 31.6 m away". The referee confirmed the planted bug by its sha256 fingerprint.

7Planting bugs is kept separate

Saboteur · npm run bug

Applies a patch to the cockpit code (for example MAP04-height-asl.patch), copies it into the running container, and seals the answer with a sha256 fingerprint.

QA · npm run qa

A separate process. It never reads the patch or the answer. It only sees the running app, the same way an operator would.

Answer · npm run bug:reveal

Shows what was planted after QA has reported, so you can check whether QA caught it. npm run bug:revert restores the original code.

8Try it

# in qa/
npm run map:discover     # agent discovers checks on the clean app (GPU)
npm run bug              # list the 15 map bugs
npm run bug -- MAP16     # plant one you choose (MAP16 = dock offset)
npm run bug:random       # or a secret one (may be none)
# reload http://localhost:4010 and look at the map
npm run qa               # visible browser: every step on screen, report card at the end
npm run bug:reveal       # what was planted
npm run bug:revert       # back to the original cockpit
