Map Lab Blueprint

A blind QA system that tests the FlytBase cockpit's Cesium 3D map as a map. It reads the live scene graph from outside the app, measures it against the WGS84 telemetry on the websocket, and uses tolerances it learned from the clean build's own noise. A separate saboteur process plants secret map bugs; the isolated inspector has to find them; a referee scores the result against a sha256 commitment.

System design

Every box is a separate OS process. Arrows show what each one reads or writes. The QA side is never told which bug was planted; the referee opens the sealed answer only after QA has reported.

Learner v2: tolerances from the build's own noise

The old learner recorded icons and camera pitch, and the inspector used hand-picked thresholds (1 m, 2°, 3 m). The new learner flies a probe drone for a calibration flight, samples the scene graph about 8 times a second against the wire, and learns each metric's error distribution on the known-good build.

Rule

tolerance = max(floor, p99 × 1.5 + margin)

Accuracy is measured against the frame the map is actually showing, and latency is measured separately, so a slow map does not look like an inaccurate one.

Is the learner worth it?

Measured, not assumed. On this build the map is drawn exactly (0 m, 0°), so the learned position, heading and height tolerances fall back to their floors; there the learner adds little over constants. It matters in two places: it learns the icon set and camera pitch (G10, G11, G15 need them without hard-coding assets), and it measures wire-to-map latency against the telemetry interval. MAP14 draws every position correctly, just one message late; only G14, which uses the learned latency, catches it.

Why it's niche

  1. It tests geodesy, not DOM text: great-circle distance, quaternion heading against local east/north, geoid vs ellipsoid height.
  2. It reads Cesium's scene graph with no product changes, through the React fiber on the map canvas.
  3. It measures wire-to-map latency per message, which catches a map that is always one message behind even though every drawn position is a real one.
  4. The bug planter and the tester are separate processes; the tester only sees the product, never the patch.
