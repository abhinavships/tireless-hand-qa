Tireless Hand · Map QA (Level 2)

26 September 2026 · Abhinav

Summary

Tireless Hand tests the FlytBase cockpit's Cesium 3D map as a map: a blind QA reads what the map draws and compares it with what each drone reported over the websocket. In the proof runs it caught 14 of 15 planted map bugs with 0 false alarms on the clean app, and found one real product bug (stale docks keep the online icon).

  • Why maps are the niche: the map is a single canvas. Normal UI tests read DOM text, so a drone drawn in the wrong place, at the wrong height or with no icon passes them unnoticed.
  • What is checked: position, height, heading, labels, icons, tracks, camera and how fast the map updates, against the drone's own telemetry.
  • How bugs are introduced: a separate saboteur process plants a secret bug; the QA never sees it; a referee checks the answer by its sha256 fingerprint.
  • Agent-discovered checks: a local LLM (Qwen2.5-Coder 7B on an RTX 5090) proposes extra checks from the map code; only those true on the clean app are kept. One of them caught a bug (MAP16, docks drawn 30 m off) that none of the hand-written checks cover.

System design

Three separate processes share nothing except the running app: the saboteur changes it, the QA observes it, the referee scores. Full diagram: Map Lab Blueprint.

Flow: Simulator → Backend :4000 → (websocket telemetry) → Cockpit :4010 Cesium map. The saboteur patches the cockpit and gives the referee a sealed answer + sha256. The QA taps the websocket frames and reads the Cesium scene graph through CDP; the blind inspector runs 15 + 8 checks and sends its verdict to the referee.

How the QA works

Every check compares one thing the map draws with the telemetry the drone sent; a difference beyond the tolerance is reported as a bug with the concrete numbers, e.g. "height label says 590 m but the drone is at 30 m".

  1. Read the map. Through Playwright (Chrome DevTools Protocol) the QA reaches Cesium's Viewer inside the page and reads each entity's latitude, longitude, height, model heading (from its rotation), label, icon file, track points, and the camera. drillPick tells it what is actually drawn at a pixel.
  2. Read the truth. Every websocket message the browser received: GPS position, height, yaw, flight status, dock location, heartbeat.
  3. Compare. The inspector creates its own test drone, takes off, runs the checks, and deletes the drone afterwards.

Learning and discovered checks

Most checks need no learning, because the truth is the drone's own telemetry; learning and discovery add 5 more bugs' worth of coverage on top.

Learner (npm run map:learn, once on the clean app). Records the icon files and camera angles, then flies a test drone for 25 s and measures the map's normal accuracy and speed: 0 m position error, 0° heading error, about 80 ms from message to map, a message every ~500 ms. The timing is what lets G14 catch a map that is one message behind.

Discovery (npm run map:discover). The agent works out extra checks itself:

  1. Propose: Qwen2.5-Coder 7B on the RTX 5090 reads CesiumMap.tsx and one real websocket message per topic and writes checks in a strict format ("this thing the map draws must equal this telemetry field"). Three rounds, about 5 s each.
  2. Verify: each check runs on every drone and dock of the clean app while a test drone flies. False checks are thrown away; that filters hallucinations.
  3. Repair: false checks go back to the LLM with what the map really showed; corrections are verified again. Checks looser than 5 m or 5° are rejected, after the LLM once "fixed" a check with a 1000 m tolerance.
  4. Keep: survivors are stored in qa/map/out/discovered.json, re-verified on every run, and run by npm run qa as D1–D8 across the whole fleet.

Result: 25 proposed, 8 kept (drone position, height, heading, track, label on every drone; dock position; height-line height and position), 17 rejected.

How to run it

Use two terminals so the bug planter and the QA stay visibly separate; start each with:

cd /Users/abhinavsden/orca/workspaces/hackathon_the_tireless_hand/numbfish/qa

Terminal 1 · Saboteur

npm run bug:status        # confirm: No bug planted
npm run bug               # list the 16 map bugs
npm run bug:random        # plant a secret bug (may be none)
npm run bug -- MAP04      # or a chosen one: MAP04 height label, MAP16 dock offset
# reload http://localhost:4010 and fly a drone to see it
npm run bug:reveal        # after QA: what was planted
npm run bug:revert        # back to the clean app

Terminal 2 · QA

npm run qa                # visible browser, every step on screen, report card at the end

Optional, one-time, clean app only

npm run map:learn         # icons, camera angles, normal speed
npm run map:discover      # LLM proposes checks; the clean app keeps the real ones
ssh -N -L 127.0.0.1:11435:127.0.0.1:11434 rtx5090@192.168.10.222   # GPU tunnel, only if needed

Stopping and cleanup. Ctrl + C stops qa, map:learn, map:discover and the tunnel; the bug commands finish by themselves. After stopping QA midway:

npm run bug:revert                                     # a planted bug stays until reverted
curl -s -X DELETE localhost:4000/api/control/fault     # clear a simulator fault
pgrep -fl tsx || echo "nothing running"

Delete any leftover MAPQA-xxxx drone in the Control panel. Never run two QA runs at once or plant while QA is running.

Limitations and next steps

The main limit: the learned and discovered parts assume the baseline app is good, so a bug already present when learning becomes "normal".

  • Baseline bugs get masked. MAP08 is invisible because the real app already has the same behaviour (G13). A correct discovered check that fails on a buggy baseline is currently discarded instead of flagged.
  • Next: report discovered checks that fail on the baseline as "possible real bug, needs review" rather than dropping them; add baseline-free physics limits (never drawn kilometres from GPS or underground).
  • The LLM misses things. It never produced a correct drone height-label check and proposed impossible ones (tracks on docks); the clean-app filter removed those.
  • Coverage gaps still open: drones that stop reporting, track reset between flights, icon visibility at far zoom, overlapping labels, map tiles offline.
  • Setup: the inspector expects qa/map/out/map-model.json to exist; discovery needs the GPU tunnel on port 11435.
