Level 1: what it is and what we're doing

FlytBase AHC SWE Hackathon · Agentic Software Testing · Team Tireless Hand (solo: Abhinav) · 2026-09-26

Is L1 just a system-design round? No. The system design is only part 1 of the submission. Part 2 is a numbered list of test scenarios, each with a real-time screen-recording video. The spec says "each one is evaluated on its own" and "a scenario without [a video] is not evaluated". Evaluators also inject deliberate bugs (mutations) into the app, and our system has to catch them. A design-only submission would score close to zero on 5 of the 6 criteria.

1. The whole problem statement, in one minute

AI now writes code faster than people can verify it. Testing is the bottleneck. The challenge: build an agentic testing system that tests a running web app from the user's point of view and returns reproducible evidence, judging behaviour by meaning, not by pixels or exact text.

The product under test is the FlytBase Cockpit starter kit: a drone operations UI (map, device list, telemetry, live video) plus a control panel and API that can take off and land drones and inject faults (socket drops, simulator offline, video freeze…).

2. Level 1: "Static UI and basic security testing"

How it's evaluated: they mutate the app and check whether our tests notice. Their examples:

  • The sign-in button is removed from a login page (email + OTP)
  • A drone is shown online when it's offline
  • The main action is pushed off screen at phone width
  • A signed-out user can open a page that needs sign-in

3. What we're building: the "Tireless Hand" system

1 · ARRANGE
Set a known state through the control API (reset, add an isolated drone, take off, inject a fault)
2 · ACT
Playwright drives the real cockpit at phone / tablet / desktop sizes
3 · ORACLE
Compare what the operator sees with ground truth (API + socket)
4 · EVIDENCE
Real-time video, screenshots, trace, and a verdict with a user-impact message
5 · PROVE
Mutation lab: inject our own bug and show the test goes red

3b. What exactly we're building for Level 1

  • A test system (qa/): Playwright + TypeScript that opens the real cockpit in a browser, puts it into known situations through the control API, and checks that what's on screen is true.
  • About 11 scenarios, each one user-meaningful (e.g. "the simulator goes offline, so drones must not look online"), each run at phone / tablet / desktop.
  • A mutation lab: we plant the same kinds of bugs the evaluators will plant (a removed button, a status flipped to online, a layout pushed off screen, a broken auth guard, HTML injection) and show each scenario goes red on the bug and stays green on the clean app.
  • Evidence per scenario: a real-time video with on-screen step captions, a screenshot, a Playwright trace, and a verdict with a plain-English failure message.
  • The write-up: system design + scenario cards + mutation matrix + video links → Google Doc → submit.

Why ours is stronger, in short:

  • Proven detection, not claimed detection: each scenario ships with a planted bug it demonstrably catches (mutation testing applied to UI tests).
  • Truth over presence: we check that statuses and values match reality, which is exactly the "online when offline" class that selector tests miss.
  • Changing conditions built in: we inject socket drops, simulator outages and video freezes, then check the UI degrades honestly and recovers.
  • Precision by design: 3× clean-pass rule, isolated test drones, a shared lock for global faults, and the LLM judge is advisory only, so there are no hallucinated failures.
  • Generic for unseen screens: declarative screen contracts + a route/auth-guard crawler cover pages evaluators may add (e.g. a login with email + OTP).
